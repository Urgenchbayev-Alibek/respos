# План тестирования RestaurantOS

Основание: ТЗ §16 (тесты и DoD), §6.1 (производительность), §19 (приёмка MVP); правила — `docs/requirements/BUSINESS_RULES.md`.
Принцип: не заявлять, что тесты прошли, если команды не запускались.

## 1. Уровни и инструменты

| Уровень | Где | Инструменты | Запуск |
|---|---|---|---|
| Unit (backend) | `respos-backend/tests/Restaurant.UnitTests` | xUnit + FluentAssertions 6.12 | `dotnet test` |
| Integration (backend) | `respos-backend/tests/Restaurant.IntegrationTests` | xUnit, `WebApplicationFactory`, Testcontainers (PostgreSQL 16) | `dotnet test` (нужен Docker) |
| Frontend unit/component | `respos-admin/src/**/*.test.tsx`, `respos-landing/src/**` | Vitest, React Testing Library, MSW (admin) | `npm run test` |
| E2E (API + SignalR) | `scripts/e2e/e2e-smoke.mjs` — сценарий ТЗ §16 против запущенного API; результаты — `docs/testing/E2E_RESULTS.md` | Node 24 + `@microsoft/signalr` | `cd scripts/e2e && npm install && node e2e-smoke.mjs` |
| E2E (UI) | `scripts/ui-smoke` (вход по ролям, обход экранов) против запущенных API + admin + landing | Playwright (Chromium) | `cd scripts/ui-smoke && npm install && npm run install-browser && npm run smoke`; в CI пока нет |
| Производительность | `scripts/e2e` (замер латентностей и доставки SignalR, `E2E_PERF_JSON=perf.json`) | Node | вручную; результаты — `E2E_RESULTS.md`; нагрузочного теста (k6) нет |

Интеграционные тесты используют настоящий PostgreSQL (Testcontainers), а не InMemory-провайдер: глобальные фильтры, `xmin`, уникальные индексы и транзакции должны проверяться на реальной СУБД. На GitHub-hosted `ubuntu-latest` Docker доступен — Testcontainers работает в CI.

## 2. Backend unit tests (Domain / Application)

## 3. Backend integration tests

### 3.1. Сквозные API-сценарии
- Auth: login → me → refresh (ротация) → повтор старого refresh → отзыв семейства → 401; logout; rate limit 6-й попытки → 429; forgot-password → 202 для несуществующего email.
- Ошибки: формат ProblemDetails (`code`, `correlationId`), отсутствие stack trace в 500.
- Pagination/sorting/filtering на `GET /orders`, `GET /ingredients`.
- Конкурентность: два параллельных изменения заказа → один получает 409 (`xmin`).

### 3.2. Защита от повторов
- `POST /payments` дважды с одним `Idempotency-Key` → один платёж, одинаковый ответ.
- Параллельные платежи на остаток заказа → суммарно не больше total.
- Повторная обработка `OrderPaidDomainEvent` → одна запись `InventoryConsumption`, движения не удваиваются.
- `send-to-kitchen` и `purchases/{id}/receive` с одним ключом → один набор тикетов / движений.

### 3.3. Складские транзакции
- Ошибка посередине операции (например, на втором ингредиенте) → откат и баланса, и движений.
- `Σ StockMovement.Quantity == StockBalance.Quantity` для каждого ингредиента после сценария.

### 3.4. Изоляция тенантов (обязательно, ТЗ §4.1, §14.1)

Фикстура: две организации A и B, в A два филиала A1, A2; пользователи с разными ролями.

| # | Тест | Ожидание |
|---|---|---|
| T-1 | Пользователь A читает `GET /orders/{id}` заказа B | 404 |
| T-2 | Пользователь A изменяет/отменяет/оплачивает сущность B по ID | 404, данные B не изменены |
| T-3 | Список `GET /menu/items` пользователя A | только сущности A |
| T-4 | Пользователь A передаёт `X-Branch-Id` филиала B | 403 `tenant.branch_forbidden` |
| T-5 | Официант с доступом только к A1 передаёт `X-Branch-Id: A2` | 403 |
| T-6 | Тело запроса содержит `organizationId`/`branchId` чужого тенанта | игнорируется, запись создаётся в своём тенанте |
| T-7 | Ссылка на чужой `tableId`/`menuItemId`/`ingredientId` в теле | 404/400, ничего не создано |
| T-8 | SignalR `JoinBranch` с чужим branchId | отказ, событие B не доставляется |
| T-9 | Отчёты/dashboard | агрегаты только своего филиала |
| T-10 | Platform admin без break-glass обращается к бизнес-endpoint тенанта | 403 |
| T-11 | Break-glass токен: чтение разрешено, запись → 403, запись в аудит есть | — |
| T-12 | Автотест-«сканер»: все `DbSet` сущностей `ITenantScoped` имеют global query filter | падает при новой сущности без фильтра |

### 3.5. Права (RBAC)
- Матрица: для каждой системной роли — набор endpoint’ов, ожидаемые 200/403 (параметризованный тест).
- Endpoint без `[HasPermission]` (кроме public/auth) → тест-рефлексия падает.
- Деактивация последнего владельца / самого себя → 422.

## 4. Frontend tests (respos-admin)

| Область | Проверки |
|---|---|
| Маршруты и роли | защищённые маршруты редиректят на `/login`; пункт меню/маршрут без права скрыт и даёт страницу 403; выбор workspace по ролям |
| Auth | токен только в памяти; при 401 — один refresh и повтор запроса; при неуспехе refresh — logout |
| Формы и валидация | Zod-схемы (пароль, бронирование, закупка); ошибка рядом с полем; маппинг `errors` из ProblemDetails на поля |
| Состояния | loading / empty / error / success у списков (DataTable) и dashboard |
| Таблицы и фильтры | фильтры попадают в query string; пагинация; сортировка |
| Создание заказа | выбор блюда → модификаторы (min/max) → количество → предпросмотр суммы → отправка на кухню с `Idempotency-Key`; повторный клик не создаёт дубль |
| KDS | отрисовка колонок; таймер (пороги цветов); на событие SignalR — инвалидирование запроса; на `onreconnected` — полный refetch |
| Касса | частичная оплата; сдача; кнопка возврата только с `payments.refund` |
| Форматирование | `formatCurrency` RU/UZ; даты в timezone филиала |
| i18n | нет «сырых» ключей на экранах в ru и uz |
| Responsive | ключевые layout’ы на 375 / 768 / 1024 / 1280 (компонентные тесты с matchMedia или визуальные E2E) |

Landing: форма заявки (валидация, honeypot `website`, 202 → успех, 429 → сообщение).

## 5. E2E-сценарий MVP (ТЗ §16)

Окружение: чистая БД + demo seed (`Seed__DemoData=true`), backend + admin запущены; два браузерных контекста (официант, повар) + кассир/менеджер.

| Шаг | Действие | Проверка |
|---|---|---|
| 1 | Администратор создаёт сотрудника (официант, филиал) | пользователь в списке; вход новым паролем/по приглашению; запись аудита |
| 2 | Официант открывает стол | стол `available → occupied` на плане зала у всех клиентов |
| 3 | Официант создаёт заказ (2 блюда, модификатор) и отправляет на кухню | заказ `submitted`; суммы совпадают с серверными |
| 4 | Кухня получает задание | тикет на KDS ≤ 2 с без перезагрузки |
| 5 | Повар: «Начать» → «Готово» | статусы тикета; заказ `in_progress → ready` |
| 6 | Официант видит готовность | toast `OrderItemReady`, статус в списке заказов |
| 7 | Кассир (смена открыта) регистрирует тестовую оплату: часть наличными + остаток картой | заказ `paid`, стол `available`, метка «Ручная отметка (демо)» |
| 8 | Склад фиксирует расход | одна запись `InventoryConsumption`, движения `consumption` по рецептуре; повтор оплаты/события не удваивает |
| 9 | Менеджер видит продажу в отчёте | `/reports/sales` и dashboard включают сумму заказа |

Дополнительно: разрыв сети на KDS → reconnect → тикеты, созданные во время разрыва, появляются (refetch).

## 6. Производительность (ТЗ §6.1 — измерить, не обещать)

| Цель | Метрика | Как измеряем |
|---|---|---|
| Типовой API-запрос ≤ 2 с при нормальной нагрузке | p95 латентности `GET /orders/active`, `GET /menu/pos`, `POST /orders`, `POST /payments` | k6/аналог; профиль нагрузки из Q14 (≈30 сотрудников, ≈500 заказов/день/филиал) с запасом ×5 |
| Основные страницы ≤ 3 с после получения данных | время до интерактивности dashboard, waiter, KDS | Lighthouse / Performance API на тестовом стенде, средний ноутбук и планшет |
| Событие на KDS ≤ 2 с | разница `occurredAt` → отрисовка тикета | лог клиента KDS в E2E, 20+ замеров |

Результаты фиксировать в этом файле (раздел «Результаты замеров») с датой, окружением и версией. Хостинг на бесплатных тарифах (sleep/cold start) может нарушать цели — отмечать это явно.

## 7. CI

`.github/workflows/ci.yml`: backend (`dotnet build/test`, включая Testcontainers), admin и landing (`lint`, `typecheck`, `test`, `build`), проверка лимита 500 строк (`scripts/check-file-length.mjs`). E2E (`scripts/e2e`, `scripts/ui-smoke`) и нагрузочные тесты в CI MVP не входят — запускаются вручную против работающего API.

## 8. Definition of Done (ТЗ §16)

Функция готова, если: use case реализован; права и tenant проверены; есть валидация; ошибки обработаны; тесты добавлены; Clean Architecture соблюдена; файл ≤ 500 строк; секретов нет; документация обновлена; build/lint/tests фактически выполнены.
