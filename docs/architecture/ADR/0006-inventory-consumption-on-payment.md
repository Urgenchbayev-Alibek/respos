# ADR-0006. Списание ингредиентов при полной оплате, идемпотентно

**Статус:** Accepted (допущение — User-Todo Q7, Q8)
**Дата:** 2026-11-10

## Контекст

ТЗ §4.9: списание идемпотентно, одно событие, связь с заказом, изменение рецептуры не переписывает историю.
Варианты события: отправка на кухню, готовность, оплата. Владелец ещё не ответил (Q7).

## Решение

- Событие списания — **полная оплата заказа** (`PaidAmount == Total` → `OrderPaidDomainEvent`).
  `BranchSettings.InventoryConsumptionTrigger = on_payment` — единственное значение в MVP.
- Handler события в той же транзакции, что и оплата (или через надёжный outbox):
  1. `INSERT InventoryConsumption (OrderId)` — **уникальный индекс по `OrderId`**; конфликт = уже списано → no-op.
  2. Для каждой не отменённой позиции берётся **активная на момент оплаты** версия `Recipe` (MenuItem + Variant),
     количество переводится в базовую единицу ингредиента (`UnitConversion`) и умножается на `Quantity` позиции.
  3. Для каждого ингредиента — `StockMovement` (`type = consumption`, `SourceType = order`, `SourceId = OrderId`,
     отрицательное количество, `BalanceAfter`) + обновление `StockBalance` в одной транзакции.
  4. Использованные версии рецептур сохраняются в `RecipeVersionsJson`.
- Продажа **может** увести остаток в минус (продажа уже состоялась) → уведомление `stock_low` + аудит (Q8).
  Ручные операции в минус не уводят, если `AllowNegativeStock = false`.
- Блюдо без рецептуры не списывается; пишется предупреждение (лог + уведомление менеджеру).
- **Возврат (refund) в MVP не возвращает ингредиенты на склад автоматически** (допущение: блюдо уже приготовлено);
  при необходимости кладовщик делает ручную корректировку. Отмена заказа до оплаты — списания не было.

## Альтернативы

- **При отправке на кухню** — списывает заказы, отменённые позже; нужна компенсация.
- **При готовности** — по позициям, много событий, сложнее идемпотентность.
- **Флаг на заказе без уникального ключа** — гонки при повторной обработке.

## Последствия

- Остатки в течение смены «отстают» от кухни до оплаты — приемлемо для MVP.
- Повторная оплата/повтор события не списывает дважды (обязательный тест).
- Если ответ на Q7 изменится — новое значение `InventoryConsumptionTrigger`; механизм идемпотентности тот же.
