# ADR-0012. Платформенный break-glass доступ

**Статус:** Accepted (реализовано)
**Дата:** 2026-11-10

## Контекст

Platform Super Admin управляет организациями и тарифами, но не должен видеть бизнес-данные ресторанов (заказы, платежи,
сотрудников) — ТЗ, BR-1.6. Для поддержки и разбора инцидентов нужен контролируемый, прослеживаемый доступ на чтение.

## Решение

- `POST /platform/organizations/{id}/access { reason }`, право `platform.tenant-data.access`, причина обязательна
  (`GrantTenantAccessHandler`).
- Выдаётся отдельный access JWT на **30 минут** для этой организации с claim `tenant_access=read_only`; **refresh token не выдаётся**.
- С таким токеном пользователь получает только org-права `*.read`, доступ ко всем филиалам организации и только методы `GET/HEAD`;
  любая запись → `403`.
- Каждая выдача аудируется (`platform.tenant_access.granted`) и видна и в системных событиях платформы, и в аудите самой организации.
- Без break-glass platform admin получает `403` на tenant-эндпоинтах; платформенные эндпоинты работают без tenant-фильтра
  (`[PlatformScope]`), даже если у админа есть членство в организации.

## Альтернативы

- Полный доступ platform admin ко всем данным — нарушает изоляцию и требования к ПДн.
- Имперсонация конкретного пользователя — сложнее, смешивает действия в аудите, даёт права на запись.
- Выгрузка данных по запросу через БД вручную — не прослеживается приложением.

## Последствия

- Доступ ограничен по времени, только чтение, полностью прослеживается.
- Отзыв выданного токена до истечения 30 мин не реализован (токен stateless) — приемлемо для MVP.
- Интеграционные тесты и E2E-скрипт проверяют: без break-glass — `403`; с ним — чтение `200`, запись `403`.
