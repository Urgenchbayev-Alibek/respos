# ADR-0005. SignalR только как канал уведомлений

**Статус:** Accepted
**Дата:** 2026-11-10

## Контекст

KDS и официантам нужны события в реальном времени (новое задание, готовность, оплата), цель ≤ 2 с (ТЗ §6.1).
Соединения рвутся (Wi-Fi в зале, сон планшета). ТЗ §1.2, §4.7: SignalR не источник истины.

## Решение

- Hub `/hubs/restaurant`, группы по филиалу/кухне/станции/пользователю (`respos-contracts/REALTIME.md`).
- События содержат только идентификаторы и статус; клиент после события **перечитывает REST**
  (инвалидация TanStack Query), после `onreconnected` — инвалидирует все запросы workspace.
- Сервер публикует события через `IRealtimeNotifier` **после commit** транзакции.
- Клиент не отправляет бизнес-команды через hub — только `JoinBranch` / `JoinKitchenStation` / `LeaveKitchenStation`.
- KDS дополнительно делает фоновый refetch раз в 30–60 с как страховку.

## Альтернативы

- **Полные данные в событии** — расхождение состояния при потерях, дублирование DTO.
- **Только polling** — проще, но нагрузка и задержка; оставлен как fallback.
- **SSE** — проще, но SignalR уже даёт reconnect, группы и fallback-транспорты.

## Последствия

- Потеря события не ломает данные — максимум задержка до refetch.
- Нужен хостинг с WebSocket и длительными соединениями (DEPLOYMENT.md).
- Несколько инстансов API потребуют backplane (Redis / Azure SignalR) — будущий ADR.
- Время доставки события измеряется (TEST_PLAN).
