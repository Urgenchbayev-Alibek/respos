# ADR-0016. Desktop-приложение для Windows: Electron + loopback-шлюз

**Статус:** Accepted
**Дата:** 2026-11-10

## Контекст

Владелец попросил выпустить существующее веб-приложение (`respos-admin`: админка, официант, KDS, касса, склад)
как обычную программу для Windows (`.exe`) — для кассовых ПК и экранов кухни. Требования:

- то же приложение, без второй кодовой базы; backend не меняется;
- один установщик для любого ресторана: адрес сервера вводится при первом запуске, пересборка «под клиента» не нужна;
- печать чеков 80 мм на термопринтер без системного диалога; режим киоска для KDS; автозапуск;
- авторизация остаётся по ADR-0003: access JWT в памяти + refresh в httpOnly cookie (`SameSite=Lax`,
  `Path=/api/v1/auth`), SignalR по ADR-0005.

Главная техническая проблема — **origin**. Если оболочка показывает собранное приложение с `file://` или со своей
схемы, а API живёт на `http://192.168.1.10:5080`, то для браузерного движка это разные сайты: refresh cookie
становится сторонней (нужны `SameSite=None; Secure` и https), нужен CORS с перечислением origin оболочки, ссылки
на файлы (`/files/...`) ломаются. Это пришлось бы настраивать на backend каждого ресторана.

## Решение

1. **Оболочка — Electron** (`respos-desktop/`, TypeScript strict, без runtime-зависимостей: main и preload
   собираются esbuild в три файла).
2. **Loopback-шлюз.** Main-процесс поднимает HTTP-сервер на `127.0.0.1:47615` (`LocalGateway`, `node:http`):
   - раздаёт собранное веб-приложение (`resources/web-dist`, SPA fallback на `index.html`);
   - проксирует `/api/*`, `/hubs/*` (HTTP и WebSocket upgrade), `/files/*`, `/health/*` на сервер из настроек.

   Окно загружает `http://127.0.0.1:47615/`, поэтому приложение и API для рендерера — **один origin**: cookie,
   SignalR и файлы работают как в браузере, без CORS и без `SameSite=None`. Порт фиксированный, чтобы origin (а с
   ним `localStorage`: тема, филиал, настройки устройства) не менялся между запусками; если порт занят — берётся
   свободный (cookie привязаны к хосту, сессия сохраняется).
3. **Правила шлюза:** слушает только `127.0.0.1`; проверяет `Host` (защита от DNS rebinding) и `Origin` (чужая
   страница в браузере на этом ПК не может ходить через прокси); тела запросов и ответов передаются потоком;
   у `Set-Cookie` убираются `Secure` и `Domain` и ставится `SameSite=Lax` (участок до шлюза — plain http на
   loopback); `Origin`/`Referer` к backend не пересылаются; недоступный сервер → `502` ProblemDetails
   `desktop.server_unreachable` (у веб-приложения есть локализованный текст); для `https://` — обычная проверка
   сертификата (плюс системное хранилище Windows), `rejectUnauthorized: false` не используется нигде.
4. **Веб-приложение собирается для оболочки флагами**, а не форком: `VITE_DESKTOP=true` (без service worker),
   `VITE_API_BASE_URL=/api/v1`, `VITE_HUB_URL=/hubs/restaurant` (относительные пути разрешаются от origin страницы).
   Веб-сборка для Vercel не меняется.
5. **Мост `window.resposDesktop`** (preload + `contextBridge`) — только `isDesktop`, `appVersion`,
   `openConnectionSettings()`, `print({ paper })`. IPC: фиксированный список каналов, проверка аргументов и
   отправителя (верхний фрейм нужного окна на нужном origin).
6. **Безопасность Electron:** `contextIsolation`, `sandbox`, без `nodeIntegration`; запрет `window.open`
   (http/https-ссылки — в системный браузер, адрес самого шлюза наружу не отдаётся) и навигации за пределы origin
   шлюза; разрешения запрещены по умолчанию; CSP для `index.html` (inline-скрипт темы — по sha256-хешу);
   fuses: RunAsNode, `NODE_OPTIONS`, `--inspect` выключены, проверка целостности asar и шифрование cookie включены.
7. **Поставка:** electron-builder — NSIS-установщик «для текущего пользователя» (без прав администратора) и
   portable-exe. Подписи кода пока нет (SmartScreen предупреждает) — сертификат в `User-Todo.md`.

## Альтернативы

- **Tauri.** Меньше установщик (системный WebView2 вместо Chromium), но: нужен Rust + MSVC toolchain (на машине
  сборки их нет, в CI — дольше и сложнее); тихая печать на выбранный принтер с заданным размером страницы в
  WebView2 требует собственного нативного кода, а в Electron это `webContents.print({ silent, deviceName,
  pageSize })`; поведение зависит от версии WebView2 на ПК ресторана (старые Windows 10 без обновлений), тогда как
  Electron везёт свой Chromium — одна и та же версия движка на всех кассах. Для POS предсказуемость и печать важнее
  ~100 МБ в установщике.
- **Загружать приложение с `file://` или своей схемы, API — напрямую.** Требует на каждом backend CORS для origin
  оболочки и `SameSite=None; Secure` для refresh cookie, то есть обязательный https даже в локальной сети
  ресторана; ломает относительные ссылки на файлы. Отклонено: backend менять нельзя.
- **Хранить refresh-токен в оболочке (safeStorage) и подставлять его самим.** Вторая схема авторизации рядом с
  ADR-0003, токен становится доступен коду оболочки. Отклонено.
- **Перехват запросов через `protocol.handle` / `webRequest` вместо HTTP-шлюза.** WebSocket через `protocol.handle`
  не проксируется, а `webRequest` не делает origin общим для cookie. Шлюз на `node:http` проще и тестируется без
  Electron (unit-тесты на фейковом сервере).
- **PWA вместо exe.** Уже есть (F8), но не даёт тихой печати, киоска и автозапуска.

## Последствия

- Плюс: backend и веб-сборка не меняются; один установщик для всех ресторанов; ADR-0003 и ADR-0005 действуют без
  исключений.
- Плюс: шлюз — обычный Node-код, покрыт unit-тестами (статика, прокси, cookie, WebSocket, защита Host/Origin);
  сценарии целиком — Playwright (dev-сборка и упакованный exe).
- Минус: установщик ~110 МБ, ~315 МБ на диске (Chromium внутри); обновление оболочки — установка новой версии
  поверх (автообновления нет); portable-версия распаковывается при каждом запуске (20–40 с).
- Минус: участок рендерер → шлюз — http на loopback. Это тот же ПК и тот же пользователь; наружу шлюз не слушает,
  но другой процесс того же пользователя может обратиться к порту (без cookie сессии он получит только то же, что
  и напрямую от сервера).
- Адрес лендинга для QR-кодов (`VITE_LANDING_URL`) вшивается при сборке веб-части, в отличие от адреса сервера.
- Тестовые переменные окружения оболочки (`RESPOS_DESKTOP_USER_DATA`, `RESPOS_DESKTOP_GATEWAY_PORT`,
  `RESPOS_DESKTOP_PRINT_CAPTURE`) описаны в `respos-desktop/README.md`; пользователям они не нужны.
- Перед коммерческим распространением нужен сертификат подписи кода (иначе SmartScreen) — задача владельца.
