# ADR-0008. Адаптер платёжного провайдера, в MVP только ручная/демо отметка

**Статус:** Accepted
**Дата:** 2026-11-10

## Контекст

ТЗ §4.11, §13: реальные банковские платежи без официальной документации и договора не подключать; данные карт
не хранить; предусмотреть `IPaymentProvider`. Ручная отметка не заменяет фискальный чек, онлайн-ККМ и эквайринг.
Провайдеры Узбекистана (Payme, Click, Uzum, Humo/Uzcard-эквайринг) — User-Todo Q4–Q6.

## Решение

- Абстракция `IPaymentProvider` в `Application/Abstractions/Payments` (`Code`, `RegisterAsync`, `RefundAsync`;
  результат со статусом и `ExternalReference`).
- Реализация `ManualPaymentProvider` в `Infrastructure/Payments`: сразу `completed`, без внешних вызовов.
  В UI подпись «Ручная отметка (демо)»; `Payment.Provider = manual`.
- Способы `cash | card | other`; `card` = кассир отметил оплату на внешнем терминале.
- Никаких PAN/CVV/данных карт в системе, логах и БД; только необязательный `ExternalReference` (номер чека терминала).
- Пречек `GET /orders/{id}/receipt` помечен «Не является фискальным чеком».
- Будущие адаптеры (Payme/Click/Uzum) — отдельные классы + webhook-эндпоинты, после договора, тестовой среды и
  отдельного ADR. Фискализация — отдельная абстракция (`IFiscalProvider`), не в MVP.

## Альтернативы

- **Сразу интегрировать провайдера** — нет договора/доступа, юридические риски.
- **Без абстракции** — дорогая замена позже.

## Последствия

- MVP пригоден для пилота только как учётная система; для коммерческого запуска нужна консультация по фискализации.
- Идемпотентность (`Idempotency-Key`, unique `(OrganizationId, IdempotencyKey)`) — основа для будущих webhook-ов.
