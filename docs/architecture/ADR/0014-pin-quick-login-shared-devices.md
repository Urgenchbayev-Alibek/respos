# ADR-0014. PIN quick login on shared devices

**Статус:** Accepted
**Дата:** 2026-11-10

## Контекст

F6: официанты, кассиры и повара работают на общих планшетах/терминалах филиала и часто меняются. Вход по e-mail +
паролю на каждом переключении слишком медленный. Нужен быстрый вход по 4–6-значному PIN, но PIN — слабый секрет
(10⁴–10⁶ вариантов): его нельзя принимать «откуда угодно», иначе это обход пароля (ADR-0003) и перебор по сети.

## Решение

1. **PIN работает только на зарегистрированном устройстве.** Менеджер (`staff.manage`) на планшете включает
   «режим общего устройства» → `POST /auth/device/register` (с `X-Branch-Id`). Сервер генерирует случайные 256 бит,
   хранит только **SHA-256 hash** (`staff_devices.token_hash`), а сырое значение отдаёт **только** в httpOnly cookie
   `device_token` (`Path=/api/v1/auth`, SameSite/Secure как у refresh, срок `Auth:DeviceTokenDays` = 180 дней).
   Устройство привязано к организации и **одному филиалу**, видно в Админке → Персонал → Устройства, отзывается
   (`POST /staff/devices/{id}/revoke`) или «забывается» на самом устройстве (`POST /auth/device/forget`, `staff.manage`).
   После регистрации сессия менеджера завершается, браузер показывает экран блокировки.
2. **PIN-логин** `POST /auth/pin-login { userId, pin }` анонимный, но без валидного cookie устройства → 401
   `device.invalid`. Пользователь выбирается из сетки аватаров `GET /auth/device/staff` (только имена сотрудников
   филиала устройства, у которых задан PIN и которым PIN разрешён) — PIN не ищется перебором по всем пользователям,
   коллизии PIN допустимы.
3. **Хранение PIN**: `PasswordHasher` (PBKDF2, как пароль) в `staff_pins`; PIN никогда не возвращается и не логируется.
   Политика: 4–6 цифр, не все одинаковые, не возрастающая/убывающая последовательность.
   Задаёт сам пользователь (`PUT /auth/pin` с текущим паролем) или менеджер (`PUT/DELETE /staff/members/{id}/pin`, аудит).
4. **Запрещено для привилегированных**: владелец, администратор (роль в любой организации) и платформенный админ
   не могут задать PIN (`pin.not_allowed`) и не входят по PIN, даже если строка PIN существует (проверка при логине
   и при каждом refresh). Им нужен пароль.
5. **Защита от перебора** (все счётчики в БД, переживают рестарт):
   - на пользователя: 5 неверных PIN → блокировка PIN-входа на 15 мин (`pin.locked`, аудит `auth.pin_locked`);
   - на устройство: 10 неверных PIN (любые пользователи) → устройство блокируется на 15 мин (`device.locked`,
     аудит `staff.device_locked`) — ограничивает перебор «по всем аватарам»;
   - rate limit `auth` (20/мин/IP); для неизвестного/неразрешённого пользователя — тот же ответ `pin.invalid` и
     проверка фиктивного hash (нет перечисления и тайминг-различий).
6. **PIN-сессия** — обычный access JWT (15 мин) + refresh cookie, но:
   - claim `branch_scope` = филиал устройства; `BranchAccessService` для такого токена отдаёт только этот филиал →
     `X-Branch-Id` другого филиала и SignalR `JoinBranch` → 403 `tenant.branch_forbidden`; `MeDto.branches` = один филиал;
   - refresh-семья связана с устройством (`pin_sessions.family_id`); `POST /auth/refresh` такой семьи требует **тот же
     активный** `device_token` (cookie того же пути) и всё ещё разрешённого пользователя, иначе токен отзывается → 401.
     Кража refresh cookie без cookie устройства бесполезна;
   - абсолютный срок `Auth:PinSessionHours` = 12 ч от PIN-входа (ротация не продлевает);
   - отзыв устройства отзывает все refresh-токены его PIN-сессий; успешный PIN-вход отзывает предыдущий refresh
     этого браузера («сменить пользователя»).
7. **Аудит**: `staff.device_registered`, `staff.device_revoked`, `auth.pin_login_succeeded`, `auth.pin_locked`,
   `staff.device_locked`, `staff.pin_set|pin_removed|pin_reset`.
8. Флаг `respos.sharedDevice` в localStorage — только UX-подсказка (показать экран блокировки / кнопку «Сменить
   пользователя»); решение всегда принимает сервер по httpOnly cookie.

## Альтернативы

- **PIN без регистрации устройства** (`{ branchId, pin }` откуда угодно) — сетевой перебор 4-значного PIN, отклонено.
- **Долгоживущий «токен устройства» в localStorage** — читается XSS, запрещено ТЗ (как и refresh в localStorage).
- **Device token = scoped JWT** — нельзя отозвать без списка отзыва; opaque-секрет с hash в БД проще и отзывается сразу.
- **Поиск пользователя по одному PIN без выбора аватара** — требует уникальности PIN и проверки hash по всем
  сотрудникам (медленно, раскрывает совпадения); отклонено.
- **WebAuthn / NFC-карты** — лучше, но требуют оборудования; возможное развитие.

## Последствия / риски

- Тот, кто физически владеет зарегистрированным планшетом, может пробовать PIN — ограничено блокировками (5/польз.,
  10/устройство за 15 мин) и аудитом; при утере планшета менеджер отзывает устройство.
- Злоумышленник с устройством может намеренно заблокировать PIN-вход сотрудников на 15 мин (DoS) — допустимо;
  пароль продолжает работать, менеджер может сбросить PIN.
- Менеджер со `staff.manage` может задать PIN сотруднику и войти от его имени — действие аудируется
  (`staff.pin_set`, `by: manager`) и даёт только права этого сотрудника в одном филиале.
- Cookie `device_token` подчиняется тем же ограничениям cross-site, что и refresh (ADR-0003): рекомендован same-site деплой.
- Счётчики неудач не атомарны при параллельных запросах (возможны 1–2 лишние попытки сверх лимита) — приемлемо.
