## A. Бизнес-правила (раздел 20 ТЗ)

- [ ] **Q1. Типы заказов.** Допущение: `dine_in` + базовый `takeaway`. Доставка — нет. *(v2: доставка реализована — см. E/V10.)*
- [ ] **Q2. Несколько филиалов в пилоте?** Допущение: архитектура multi-branch, в пилоте 1 филиал.
- [ ] **Q3. Бронирования в MVP?** Допущение: да, базовые (с проверкой пересечений).
- [ ] **Q4. Способы оплаты.** Допущение: `cash`, `card` (ручная отметка), `other`. Payme/Click/Uzum — не подключены.
- [ ] **Q5. Местные платёжные провайдеры** (Payme, Click, Uzum, Humo/Uzcard-эквайринг)? Нужны договор и доступ к тестовой среде. Сейчас — `ManualPaymentProvider` с пометкой «Демо». *(v2: адаптеры Payme/Click написаны, ждут реквизитов — см. E/V1–V3.)*
- [ ] **Q6. Онлайн-ККМ / фискализация** (soliq.uz, виртуальная касса)? Сейчас пречек с пометкой «Не является фискальным чеком». Нужна консультация местного специалиста.
- [ ] **Q7. Когда списывать ингредиенты?** Допущение: **при полной оплате заказа** (одно событие, идемпотентно).
- [ ] **Q8. Отрицательные остатки.** Допущение: ручные операции не могут увести остаток в минус (настройка филиала `AllowNegativeStock=false`). Автосписание при продаже **может** увести в минус (продажа уже состоялась) — создаётся уведомление и запись аудита. Подходит?
- [ ] **Q9. Кухонные принтеры?** Допущение: нет, только KDS-экран.
- [ ] **Q10. Офлайн-режим?** Допущение: нет (ТЗ исключает).
- [ ] **Q11. RU и UZ с первого релиза?** Допущение: да, оба (узбекский — латиница). Тексты UZ сделаны машинно/черново — **нужна вычитка носителем**.
- [ ] **Q12. Налог, сервисный сбор, скидки.** Допущение: настройки филиала `serviceChargePercent` (по умолчанию 0%) и `taxPercent` (0%, начисляется сверху). Скидка на заказ — сумма или процент, только с правом `orders.discount.apply` и причиной. Нужно уточнить: НДС уже входит в цены меню? Сервисный сбор 10–15%?
- [ ] **Q13. Разделение счёта / частичная оплата.** Допущение: частичная оплата есть (несколько платежей разными способами), разделение счёта по позициям — после MVP. *(v2: разделение счёта реализовано — поровну, по позициям, по суммам.)*
- [ ] **Q14. Ожидаемая нагрузка** (пользователей, заказов в день)? Допущение: до 30 сотрудников, до 500 заказов/день на филиал.

## D. Известные ограничения MVP (решить позже, не блокируют пилот)

- [ ] **L1.** Блокировка пользователя глобальная: если сотрудник работает в двух организациях, блокировка в одной блокирует и в другой. Для пилота (1 организация) не важно.
- [x] **L2.** (решено: grace-окно 15 с, ADR-0003) Одновременное обновление сессии в двух вкладках браузера может сработать как «повторное использование refresh-токена» → потребуется войти заново. Можно смягчить grace-периодом 10–30 с.
- [ ] **L3.** Станция кухни и стоп-лист блюда — на уровне организации, а не филиала (нормально для 1 филиала, Q2). *(v2: решено — переопределения цены, стоп-листа и станции по филиалам, F4.)*
- [ ] **L4.** Вне Development миграции БД применяются отдельной командой до старта API (см. `docs/deployment/DEPLOYMENT.md`).
- [x] **L5. Диск C: был заполнен (0 МБ).** РЕШЕНО 10.11.2026: очищены кэши (Gradle, npm, pip, Windows Update, старые IntelliJ, .cache, снапшоты эмуляторов) — свободно ~66 ГБ. Во время работы я очистил кэш npm (`npm cache clean --force`, 6 ГБ — это только кэш загрузок, восстанавливается сам). Освободите место на C: (Docker Desktop ~5 ГБ, Temp ~1.5 ГБ) — иначе npm/Docker/Testcontainers будут падать с ENOSPC.
- [ ] **L6. Docker после нехватки места.** Из-за заполненного C: в Docker повредился слой базового образа `mcr.microsoft.com/dotnet/aspnet:8.0` (нулевые DLL). Я удалил этот образ и build cache (всё перекачивается автоматически) — после этого образ API собирается и запускается (`docker compose --profile full up`, проверены health/login). Если увидите `Invalid framework config.json` — повторите: `docker builder prune -af && docker rmi mcr.microsoft.com/dotnet/aspnet:8.0`.

## E. v2 (10.11.2026) — что нужно от владельца

Код v2 (F1–F8) слит и проверен на тестовых/демо-данных. Внешние сервисы **не подключены**: в интерфейсе они честно
показаны как «Не подключено». Чтобы включить их, нужны ваши договоры и реквизиты (в репозиторий и в `VITE_*` их не кладём).

- [ ] **V1. Payme.** Договор мерчанта и доступ в кабинет. Передать на сервер (env): `PaymentProviders__Payme__MerchantId`,
  `PaymentProviders__Payme__Key`, для песочницы `PaymentProviders__Payme__TestMode=true`. В кабинете Payme указать URL
  `https://<api-домен>/api/v1/payments/providers/payme/callback`. После этого провайдер включается по филиалам в «Настройки → Платёжные провайдеры».
  Адаптер написан по публичному Merchant API и покрыт тестами на подписи/идемпотентность, но **с реальной песочницей Payme не проверялся**.
- [ ] **V2. Click.** Договор и реквизиты: `PaymentProviders__Click__ServiceId`, `__MerchantId`, `__SecretKey` (+ `__TestMode`). URL для Prepare/Complete:
  `https://<api-домен>/api/v1/payments/providers/click/callback`. Так же: **с реальным Click не проверялся**.
- [ ] **V3. Uzum.** Только заготовка (всегда «Не подключено»): нужна официальная документация мерчант-API Uzum и тестовый доступ — тогда адаптер можно дописать.
- [ ] **V4. Фискализация (онлайн-ККМ).** Не подключена (`IFiscalProvider` → `none`), пречек не является фискальным чеком. См. Q6: нужен выбор оператора и консультация.
- [ ] **V5. Telegram-уведомления владельцу.** Создать бота у @BotFather, прислать токен и chat id (личный или группы) — вводятся в «Интеграции → Telegram-бот»
  (хранятся зашифрованно, наружу отдаются только в виде `****1234`). Проверка — кнопка «Отправить тест».
- [ ] **V6. SMS (Eskiz.uz).** Договор с Eskiz: email, пароль, согласованное имя отправителя и шаблоны SMS → «Интеграции → SMS». Без этого подтверждения броней по SMS не уходят.
- [ ] **V7. Почта (SMTP).** Хост, порт, логин/пароль, адрес отправителя → «Интеграции → Почта» (для организации) и/или `Integrations__Smtp__*` на сервере
  (приглашения и сброс пароля для всей платформы). Пока не задано — письма пишутся в лог (как в MVP, T6).
- [ ] **V8. Программа лояльности — проверить значения по умолчанию.** Сейчас: выключена; начисление 5 % от итога оплаченного заказа; бонусами можно
  оплатить до 30 % счёта; минимальная сумма заказа 0; срок жизни бонусов — бессрочно; 1 бонус = 1 сум. Решить: (а) эти проценты; (б) начислять ли бонусы
  на сервисный сбор и стоимость доставки (сейчас база начисления — весь итог заказа); (в) кто может менять программу — сейчас только владелец/администратор (`settings.manage`).
- [ ] **V9. Права ролей v2.** Официант и кассир могут создавать гостей и списывать бонусы; кассир ведёт доставку; менеджер — график, табель и PIN. Проверьте, что это подходит (см. `respos-contracts/v2/`).
- [ ] **V10. Доставка.** Стоимость доставки задаётся одной суммой на филиал («Филиал → QR-меню и доставка»). Нужны ли зоны/расчёт по расстоянию и приём онлайн-заказов с сайта?
- [ ] **V11. Онлайн-бронирование.** Часы приёма броней одни для всех филиалов (10:00–22:00, шаг 30 мин, стол на 120 мин) — подтвердить или прислать свои.
  Лендинг берёт филиал из `VITE_PUBLIC_BRANCH_SLUG` (по умолчанию `demo`) — **при следующем деплое лендинга на Vercel задайте эту переменную** (старая `VITE_PUBLIC_BRANCH_ID` больше не используется).
- [ ] **V12. Production-обновление до v2.** Перед запуском новой версии API применить миграцию `V2Features` (только добавляет таблицы/колонки, см. L4 и DEPLOYMENT.md)
  и сохранить ключи шифрования интеграций (таблица `data_protection_keys` или `DataProtection__KeysPath`): при их потере секреты интеграций придётся ввести заново.
- [ ] **V13. PIN-вход на общих планшетах.** Работает только на устройстве, которое подключил менеджер («Персонал → Общие устройства»). Демо-PIN (2580/3690/1470) создаются
  **только в Development**; в рабочей системе сотрудник задаёт PIN сам в профиле или его задаёт менеджер.
- [ ] **V14. Вычитка UZ/EN.** Тексты новых экранов на узбекском и английском сделаны машинно — нужна вычитка носителем (как Q11).
